# Configuring a customer

> [!STORY] What did you actually do all week?
> The four interview rounds before you joined never reached the concrete answer to "what does configuring a customer actually mean?". The docs describe the screens. The answer turned up inside the repo: a customer's workspace has a small set of defaults, set by one API call, and a large share of the craft is in four text fields.
> So the FDE's real skill, a lot of the time, is prompt engineering as customer configuration.

## The workspace defaults

Each customer workspace has defaults, pushed with `PUT /api/workspace/defaults`. They carry a `prompts` object with four fields:

- **`felix_system`:** the system prompt for the in-product assistant, for that customer.
- **`label_analysis_system`:** the big one. How conversations become topics with sentiment and impact (chapter 2.2).
- **`conversation_diagnosis_system`:** how a needle mover is diagnosed and written up.
- **`query_generator_additional_instructions`:** extra steering for the SQL the agent writes (chapter 2.6).

Plus non-prompt defaults: which columns and filters the accounts list shows (`designation_accounts_columns`, `designation_accounts_filters`), how strongly conversations count in predictions (`conversations_prediction_weight`), and the order of account strategy properties (`account_strategy_properties_ordering`).

## What the job really is

You read a customer's real conversations. You work out which signals matter in **their** business. You encode that as topic definitions and worked examples. A restaurant tool and an HR tool do not share a definition of "pricing".

## The checklist

Aadarsh's own checklist for configuring a workspace end to end:

1. **Data models:** accounts, users, contacts, activity, subscriptions, products, usage, tickets, conversations.
2. **Retention tags:** the churn and retention audiences that train the model.
3. **Journey funnel:** the stages a customer moves through.
4. **Needle movers:** which types are on and how they are tuned.
5. **Notes.**
6. **Workspace grounding:** the facts about the customer's own business that the assistant should know.

Then predictions. Then agents.

## The five things you actually ship

From the first weeks of record, everything you and Aadarsh shipped is one of five things:

1. **A report.** HTML or PowerPoint, generated by a flow from live data. The Go-Live readiness report, the weekly status deck, the renewal watch.
2. **A sync.** CRM writeback, dataset upserts, a table pushed into the customer's own tool.
3. **A dashboard or data app.** Sometimes embedded in the customer's tool, sometimes a link to their own customer.
4. **An alert.** Email or Slack to a named person, escalating to a named person above them.
5. **An approach doc.** When the ask is not yet a build. Arun asked for exactly this on the adoption tooling: come up with an approach, let us review and agree before you start implementing. A document that is easy to review.

Four of the five end at a named human. That is not a coincidence. It is chapter 3.6.

## Reading a customer before a call

A short routine that has paid off:

1. Read the customer's folder in the work repo: what they sell, who the people are, what is open.
2. Read the most recent standup notes and the shared channel for that customer.
3. Read the current month's release notes, so you do not ask for something that already shipped.
4. Run the five-step diagnostic from chapter 4.0 against anything that looks wrong.
5. Know one number you verified yourself, and one thing you are assuming. Say which is which.

## Traps

- Writing a generic label prompt for a customer. It will pass tests and mislabel their real conversations.
- Configuring all six checklist items and shipping no agent. A configured workspace nobody uses is not a result.
- Skipping the grounding step. The assistant will then guess the customer's business.
